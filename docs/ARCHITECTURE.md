# Architecture

## System Context

FraudShield sits between the payment gateway and the settlement engine. When a transaction arrives, two things must happen:

1. A fraud score must be produced within approximately 3 seconds (streaming path) so the payment gateway can approve, hold, or decline the transaction before settlement.
2. The transaction must land in the analytics warehouse within 15 minutes (batch path) so the fraud team can run investigations and the ML pipeline can retrain on fresh data.

These are fundamentally different latency and throughput requirements, which is why the system uses dual processing paths rather than attempting to serve both needs from a single pipeline.

## Architecture Decision Records

### ADR-001: Kinesis Data Streams over MSK (Kafka)

**Decision:** Use Kinesis Data Streams for real-time ingestion.

**Context:** The team evaluated MSK (managed Kafka) and Kinesis. Peak volume is approximately 50K events per minute, which is modest by Kafka standards.

**Rationale:**
- Kinesis costs roughly 60% less per month than a 3-broker MSK cluster at this volume (2 shards versus 3 brokers)
- Operational overhead is lower with no broker patching or partition rebalancing
- Native Lambda consumer integration eliminates consumer group management
- Shard-based scaling maps well to predictable, diurnal traffic patterns

**Tradeoff:** Kinesis has a 1MB record size limit and 7-day maximum retention. Transaction events average 2KB, so the size limit is not a constraint. Replay beyond 7 days is handled by reading from the S3 bronze layer.

**Conditions that would change this decision:** Multi-region replication requirements, complex broker-level routing or filtering, sustained throughput above 500K events per minute, or a team with deep existing Kafka expertise.

### ADR-002: Lambda over ECS/Fargate for Stream Processing

**Decision:** Use Lambda for real-time fraud scoring.

**Context:** The scoring function loads a serialized model, enriches the transaction with lookup data from DynamoDB, and returns a score. Typical execution time is 200-800ms.

**Rationale:**
- Scales to zero during off-peak hours; traffic is heavily diurnal
- No container orchestration overhead
- Kinesis-Lambda integration handles checkpointing and error handling automatically
- Cold start latency is mitigated by provisioned concurrency during business hours

**Tradeoff:** Lambda enforces a 15-minute timeout and 10GB memory limit. The scoring function uses approximately 512MB and completes in under 1 second, well within bounds. If scoring complexity increases (graph lookups, multi-model ensemble), these limits may become restrictive.

**Rejected alternative:** Kinesis Data Analytics (managed Flink) was prototyped. It worked correctly but was excessive for a stateless scoring use case, and the managed Flink service cost was approximately 3x higher for equivalent throughput.

### ADR-003: AWS Glue over EMR for Batch Processing

**Decision:** Use AWS Glue with PySpark for batch ETL.

**Context:** Daily batch jobs process the previous day of transactions: deduplication, enrichment, feature computation, and aggregation into gold-layer tables.

**Rationale:**
- Serverless execution eliminates cluster lifecycle management
- Built-in job bookmarks support incremental processing
- Glue Data Catalog serves as a Hive-compatible metastore
- Crawler integration supports schema discovery for new data sources

**Tradeoff:** Glue cold start is 2-3 minutes minimum. For jobs that run once daily, this is acceptable. For hourly micro-batch workloads, the overhead accumulates. Glue is also more expensive per DPU-hour than equivalent EMR spot instances, but the operational savings justify the premium at current scale.

**Known constraint:** The Glue PySpark environment lags behind upstream Spark releases. The platform is currently limited to Spark 3.3 features.

### ADR-004: Redshift Serverless over Athena

**Decision:** Use Redshift Serverless for the analytics warehouse.

**Context:** Analysts and Power BI require sub-second query performance on aggregated data. Finance runs complex window function queries for chargeback forecasting.

**Rationale:**
- Materialized views accelerate dashboard queries
- Concurrency scaling handles the parallel query pattern generated by Power BI
- COPY command from S3 is well-optimized for bulk loading
- Query performance on complex joins and aggregations exceeds Athena

**Alternative considered:** Athena would be less expensive for ad-hoc queries and requires no infrastructure. However, the Power BI connector experience is more reliable with Redshift, and repeated dashboard queries benefit from result caching and materialized views.

### ADR-005: Medallion Architecture (Bronze/Silver/Gold)

**Decision:** Implement bronze, silver, and gold data layers on S3.

**Layout:**
```
s3://fraudshield-lake-{env}/
├── bronze/
│   ├── transactions/
│   │   └── year=2024/month=01/day=15/hour=10/
│   │       └── kinesis-shard-00000-{timestamp}.parquet
│   ├── chargebacks/
│   └── merchants/
├── silver/
│   ├── transactions_clean/
│   │   └── dt=2024-01-15/
│   │       └── part-00000.parquet
│   ├── transactions_enriched/
│   └── chargebacks_matched/
├── gold/
│   ├── fraud_scores_daily/
│   ├── merchant_risk_profiles/
│   ├── chargeback_forecasts/
│   └── kpi_summary/
└── _metadata/
    ├── schemas/
    └── quality_reports/
```

**Partitioning strategy:**
- Bronze: partitioned by ingestion time (year/month/day/hour). Aligns with Kinesis delivery cadence and supports targeted reprocessing of specific time windows.
- Silver: partitioned by event date (dt=YYYY-MM-DD). Business queries are almost always date-ranged.
- Gold: partitioned by date, with additional dimensions where appropriate (merchant_category for risk profiles).

**File format:** Parquet with Snappy compression throughout. Target file sizes of 128-256MB in silver and gold layers to balance Spark partition efficiency against S3 GET request costs. Bronze files are smaller due to Kinesis write frequency; a nightly compaction job consolidates them.

**Iceberg/Delta Lake consideration:** Both were evaluated. Iceberg is the stronger long-term choice due to time travel, schema evolution, and hidden partitioning. The decision to use plain Parquet for the initial implementation was based on: (a) Glue Iceberg support maturity at the time of development, (b) team familiarity, and (c) low schema change frequency. Migration to Iceberg is the highest-priority item on the platform roadmap.

## Data Flow

### Streaming Path
```
Payment API
    |
    v
Kinesis Data Stream (2 shards, 2MB/s write capacity)
    |
    ├──> Lambda (fraud scorer)
    |       - Loads model from S3 (cached in /tmp across warm invocations)
    |       - Enriches from DynamoDB (merchant profiles, user history)
    |       - Writes score to DynamoDB (fraud_decisions table)
    |       - Publishes to SNS if score exceeds threshold
    |
    └──> Kinesis Firehose
            - Buffers 5 minutes or 128MB (whichever comes first)
            - Writes Parquet to S3 bronze/transactions/
            - Applies Glue table schema for catalog registration
```

### Batch Path
```
S3 Bronze
    |
    v
Airflow DAG (daily, 02:00 UTC)
    |
    ├──> Glue Job: bronze_to_silver
    |       - Deduplication (transaction_id as idempotency key)
    |       - Schema validation and data quality checks
    |       - Type casting, null handling
    |       - Output: silver/transactions_clean/
    |
    ├──> Glue Job: enrich_transactions
    |       - Join with merchant profiles
    |       - Join with chargeback data (available at T+3 lag)
    |       - Compute velocity features (txn count per card: 1h, 24h, 7d)
    |       - Output: silver/transactions_enriched/
    |
    ├──> Glue Job: build_gold_tables
    |       - Aggregate to gold/fraud_scores_daily/
    |       - Aggregate to gold/merchant_risk_profiles/
    |       - Execute chargeback forecast model
    |       - Output: gold/*
    |
    ├──> Redshift COPY
    |       - Truncate-and-load for dimensions
    |       - Append for facts (with deduplication check)
    |       - Refresh materialized views
    |
    └──> Quality Report
            - Great Expectations validation suite
            - Results written to S3 _metadata/quality_reports/
            - CloudWatch alarm triggered if critical checks fail
```

## Failure Handling

**Kinesis Lambda failures:** A dead-letter queue (SQS) captures events after 3 retry attempts. A separate Lambda function drains the DLQ every 15 minutes and writes failed events to `bronze/transactions_failed/`. A CloudWatch alarm fires if DLQ depth exceeds 100 messages.

**Glue job failures:** Airflow retries each job twice with exponential backoff. If a job fails 3 times, the DAG is marked as failed and a PagerDuty alert is triggered. All jobs are idempotent (target partition is overwritten), making retries safe.

**Late-arriving data:** Chargebacks arrive between T+3 and T+45 from card networks. The enrichment job handles this by reprocessing a sliding 45-day window when new chargeback files land. This approach is computationally wasteful but operationally simple. CDC-style incremental updates would be more efficient but the chargeback volume is low enough that full reprocessing is acceptable.

**Schema changes:** The bronze layer accepts all data without schema enforcement (schema-on-read). The silver layer validates incoming records against a registered schema in the Glue Data Catalog. Unrecognized fields are dropped at the silver boundary and a warning is logged, allowing the team to decide whether to evolve the schema.

## Security

- All S3 buckets encrypted with SSE-KMS using a customer-managed key
- Kinesis streams encrypted in transit and at rest
- Redshift cluster deployed in a private subnet, accessible only via VPC endpoint
- IAM roles follow least-privilege principles; each Glue job has a dedicated role scoped to specific S3 prefixes
- PII fields (card number, cardholder name) are tokenized at the ingestion layer; the scoring Lambda never processes raw PAN data
- VPC flow logs enabled; all API calls logged to CloudTrail
